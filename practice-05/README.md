## Наблюдение за HTTP

| Запрос | Статус | `ok` | Тело |
|---|---:|---|---|
| `/api/health` | 200 | true | `{ data: { status: "ok" } }` |
| `/api/tasks` | 200 | true | `{ data, meta }` |
| `/api/tasks?completed=false&priority=high` | 200 | true | id `[4, 34]` |
| `/api/tasks/25` | 200 | true | `{ data: Task }` |
| `/api/tasks/999` | 404 | false | `{ error: { code: "TASK_NOT_FOUND", ... } }` |
| `/api/categories` | 200 | true | `{ data, meta }` |

`fetch` не отклоняется при 404. Поэтому `requestJson` ловит только отказ самого `fetch`, а обработка `Response` идёт отдельно — HTTP-ошибка не маскируется как сетевая.

## Ответственность модулей

- `api-client.js` — транспорт: `buildUrl`, GET, `Accept: application/json`, `AbortSignal.timeout` + `AbortSignal.any`, проверка `Response`, `ok`, `Content-Type`, JSON, единый `ApiError`.
- `task-api.js` — маршруты и схема: нормализация фильтров, проверка задач и категорий, уникальность `id`, `meta.total`, `Promise.all` в `loadInitialData`.
- `main.js` — контрольный сценарий. `variant.js` — только данные варианта.

## Общий клиент

`buildUrl` склеивает без двойного `/`, кодирует через `URLSearchParams`, пропускает `undefined`/`null`/`""`, сохраняет `false` и `0`, не мутирует `query`.

`requestJson`:

1. `buildUrl`;
2. `AbortSignal.timeout(timeoutMs)`;
3. при внешнем сигнале — `AbortSignal.any([signal, timeout])`;
4. `fetch` в отдельном `try`;
5. при отказе: `aborted` (если внешний сигнал сработал), иначе `timeout` (если тайм-аут), иначе `network`;
6. проверка `Response`;
7. `!ok` → `ApiError(http)` с `status`, `code`, `details`, `url` из `payload.error`;
8. `204` → `null`;
9. неверный `Content-Type` → `invalid-response`;
10. ошибка `response.json()` → `invalid-response` с `cause`.

## Предметный клиент

Разрешены только `completed`, `priority`, `categoryId`, `q`; иные ключи — `TypeError` до запроса.

| Метод | Путь | Проверки |
|---|---|---|
| `getTasks(filters)` | `/tasks` | схема, уникальность `id`, `meta.total === data.length` |
| `getTaskById(id)` | `/tasks/:id` | схема, `task.id === id` |
| `getCategories()` | `/categories` | схема, уникальность `id` |
| `loadInitialData(filters)` | `/tasks` + `/categories` | `Promise.all` |

Схема задачи: `id` > 0, `title` 1–100 после `trim`, `completed` boolean, `priority` ∈ `low|medium|high`, `categoryId` > 0. Категория: `id` > 0, `name` 1–100 после `trim`. Нарушение → `ApiError(invalid-response)`.

## Виды ошибок

| `kind` | Причина |
|---|---|
| `http` | `!response.ok`; сохраняются `status`, `code`, `details`, `url` |
| `network` | отказ `fetch` без отмены/тайм-аута |
| `invalid-response` | не `Response`, неверный `Content-Type`, битый JSON, несоответствие схеме |
| `timeout` | сработал `AbortSignal.timeout` |
| `aborted` | сработал внешний `AbortController` |

## Последовательное и параллельное ожидание

`/api/debug/delay?ms=100`, три прогона:

| Сценарий | 1 | 2 | 3 |
|---|---:|---:|---:|
| `await delay(100); await delay(100)` | [ ] | [ ] | [ ] |
| `Promise.all([delay(100), delay(100)])` | [ ] | [ ] | [ ] |

Ожидается ~200 мс против ~100 мс. Искусственные задержки в итоговый код не включены. `loadInitialData` создаёт оба Promise до `await`; `Promise.all` не отменяет вторую операцию при отказе первой.
