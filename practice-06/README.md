## 5. Устройство HTTP-клиента и предметного API

**`src/api-client.js`** — общий клиент. Экспорт: `ApiError`, `buildUrl`, `createApiClient`. `requestJson(path, { method, query, body, signal, timeoutMs })`:

- допустимые методы — `GET/POST/PATCH/DELETE` (иначе `TypeError` до сети); `GET` с телом — `TypeError`;
- `Accept: application/json` всегда; `Content-Type: application/json` — только при наличии тела (`JSON.stringify`);
- тайм-аут `AbortSignal.timeout`, комбинируется с внешним `signal` через `AbortSignal.any`;
- не-OK → `ApiError` с `status/code/details/url`; `204` → `null` **до** `response.json()`;
- у остальных успешных — проверка `Content-Type` и разбор JSON в `try/catch`;
- виды ошибок: `http`, `network`, `invalid-response`, `timeout`, `aborted`.

**`src/task-api.js`** — предметный слой над `/tasks` и `/categories`:

- `getTasks(filters, {signal})`, `getTaskById(id, {signal})`, `getCategories({signal})`, `loadInitialData(filters, {signal})` (параллельно `getTasks` + `getCategories`);
- `createTask(draft, {signal})` (`POST`), `updateTask(id, changes, {signal})` (`PATCH`), `setTaskCompleted(id, completed)`, `deleteTask(id)` (строго `null`), `resetDemoData()`;
- схема ответа проверяется (`isTask`, `isCategory`, уникальность `id`, `meta.total`), ошибки схемы → `invalid-response`;
- DOM не используется, пользовательские тексты не формируются.

**`src/form-validation.js`** — `validateTaskDraft(draft, categories)` → `{ valid, value, errors }`. Нормализует `title` (trim, 1–100), `priority` (из `low/medium/high`), `categoryId` (число, есть в загруженных категориях). Вход не мутирует.

**`src/task-view.js`** — `createTaskElement` строит `li.task-card[data-task-id]` с тремя `button[data-action]` (`toggle`/`edit`/`delete`); `renderTaskList` заменяет содержимое через `replaceChildren`. Пользовательский текст — только `textContent`.

**`src/app-controller.js`** — единственный модуль, связывающий API и view. Хранит `tasks`, `categories`, `filters`, `editingId`, активный `AbortController`, номер загрузки. Не импортирует `dom-app.js`, не обращается к `document`.

## 6. Схема асинхронных состояний

| Состояние | Когда | Что видно |
|---|---|---|
| `loading` | запрос в полёте | `aria-busy="true"`, «Загрузка задач…» |
| `ready` | пришли непустые данные | карточки, `#task-total` |
| `empty` | OK, `tasks.length === 0` | «По выбранным условиям задач нет.» |
| `error` | сеть/HTTP/схема | причина из `messageForError`, кнопка `#retry-load` |

Плюс блокировка мутации: `setMutationPending(true)` на время `POST/PATCH/DELETE + refresh`; снимается в `finally` всегда.

`empty` — нормальный результат фильтра, не ошибка. `error` — исключительное состояние с сообщением и retry.

## 7. Защита от устаревшего ответа

Два независимых механизма:

1. **Отмена** — `state.loadController.abort()` перед каждой новой загрузкой; `signal` проходит через `api.getTasks`/`loadInitialData` в `fetch`.
2. **Номер запуска** — `state.loadSeq` инкрементируется на каждой загрузке; результат применяется только при `seq === state.loadSeq && !state.destroyed`. Это страховка на случай, когда `fetch` уже отдал данные в момент `abort()`.

Отмена (`signal.aborted` или `ApiError.kind === "aborted"`) **молча выходит** — без `notify` и без `setListState("error")`.

## 11. Ответы на контрольные вопросы (кратко)

1. **`fetch` и 404/500.** `fetch` отклоняется только при сетевой ошибке/отмене; любой HTTP-статус — валидный ответ. Поэтому статус проверяется явно (`response.ok`) — иначе 502 прокси маскировался бы под сетевую ошибку.
2. **Порядок проверок.** `response.ok` → (не OK) чтение тела и `ApiError{status,code,details}` → `204 → null` → `Content-Type` содержит `json` → `json()` в `try/catch`. Сначала HTTP-ошибка, потом 204, потом формат.
3. **POST vs PATCH.** `POST /tasks` — создание (`title`, `priority`, `categoryId`; `id`/`completed` назначает сервер), `201 + Location`. `PATCH /tasks/:id` — частичное изменение (часто только `completed`), `200`, `id` в URL, не в теле.
4. **201 + Location.** `201` — ресурс создан; `Location` — канонический URL нового ресурса (`/api/tasks/35`) для `GET` и кэширования.
5. **Почему нет `response.json()` при 204.** Тела нет; `json()` на пустой строке бросит `SyntaxError`. Возвращаем `null` **до** проверки `Content-Type`.
6. **Preflight / no-cors.** `OPTIONS` отправляется при не-простых методах/заголовках (`Content-Type: application/json` для `POST/PATCH`). `no-cors` делает ответ «opaque» — ни `status`, ни `headers`, ни тела. Решение — CORS-заголовки на сервере.
7. **`empty` vs `error`.** `empty` — успешный `GET` с пустой выборкой (норма); `error` — запрос не дошёл или сервер вернул ошибку (исключение, retry). Соответственно разные ветки `setListState`.
8. **Почему не `localStorage`.** Сервер — единственный источник истины (`id`, `completed`, фильтрация — на сервере). Локальная копия даст рассинхрон между вкладками/перезапусками. `localStorage` остаётся только как ловушка в тесте.
9. **Зачем повторный `GET`.** Пессимистичная модель: показываем только подтверждённое сервером. После мутации задача могла выйти/войти в активный фильтр — узнаём это только из нового `GET`.
10. **Гонка фильтров.** Пользователь ставит `A`, затем быстро `B`; два `GET ?A` и `?B` завершаются в произвольном порядке. Без защиты применяется `?A`, хотя выбран `?B`.
11. **Почему одного `AbortController` мало.** `fetch` мог уже отдать ответ в момент `abort()` (Promise зарезолвится не `AbortError`), а сторонние `fetchFn` могут игнорировать сигнал. Второй механизм — `state.loadSeq`: применяется только ответ на последний запуск.
12. **Почему отмена ≠ ошибка.** Отмена — осознанное действие (смена фильтра, refresh). Показ «не удалось загрузить» при каждой смене фильтра — ложная ошибка. Поэтому `aborted` выходим молча.
13. **Клиент vs сервер.** Клиент — UX-валидация (`title` 1–100, `priority`, существование `categoryId`). Сервер обязан повторять всё (клиент обходится curl’ом) + проверять то, чего клиент не знает: актуальность категории, лимиты, уникальность.
14. **Зачем `view` параметром.** Инверсия зависимостей: контроллер не знает про DOM. Тесты без DOM (`modules.checks.js`), замена адаптера без правок контроллера, чистая граница ответственности.
15. **Почему `textContent`.** Данные с сервера недоверенные. `innerHTML` исполнил бы `<img onerror=...>`; `textContent` выводит строку буквально. Все тексты карточек и кнопок строятся через `createElement` + `textContent`.
