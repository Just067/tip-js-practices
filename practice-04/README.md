## 3. Эксперименты с формой и JSON

| № | Прогноз | Фактический результат | Объяснение |
|---:|---|---|---|
| 1 | При пустом обязательном названии браузер не должен инициировать `submit`. | Событие `submit` не дошло до прикладного обработчика, `validity.valid` было `false`, браузер показал стандартное сообщение. | Нативная проверка HTML блокирует отправку до вызова обработчика формы. |
| 2 | Строка из пробелов пройдёт `required`, но будет отклонена прикладной проверкой после `trim`. | `submit` сработал, `validateTaskDraft` вернул ошибку поля `title`, сообщение показано через `setCustomValidity` и `reportValidity`. | `required` проверяет только непустоту строки, но не её нормализованное содержимое. |
| 3 | `FormData.get()` вернёт строки; в обработчике нужно вызвать `preventDefault()`; название будет нормализовано. | Получены строки `id = "20"`, `title = "  Изучить localStorage  "`, `priority = "high"`. После проверки получено `{ id: 20, title: "Изучить localStorage", priority: "high" }`. | Значения формы имеют строковый тип, поэтому id явно преобразуется через `Number`, а название — через `trim`. |
| 4 | `getItem()` вернёт строку JSON или `null`; для получения объекта нужен `JSON.parse`. | `getItem()` вернул строку, после `JSON.parse` получен объект `{ version: 1, tasks: [...] }`. | `localStorage` хранит только строки. |
| 5 | Повреждённый JSON вызовет исключение `JSON.parse`, которое нужно перехватить. | При записи `{broken-json` возник `SyntaxError`; приложение перешло на исходный набор и показало предупреждение. | Разбор JSON находится внутри `try/catch`, поэтому повреждённая запись не ломает запуск приложения. |

## 5. Проверки формы

В `form-validation.js` реализована чистая функция `validateTaskDraft(draft, tasks, editingId = null)`. Она возвращает либо `{ ok: true, value }`, либо `{ ok: false, errors }`, где `errors` содержит только поля с ошибками.

**Правила создания задачи:**

| Поле | Правило |
|---|---|
| `id` | После `Number` — положительное безопасное целое число; такого id нет в `tasks`; пустая строка не принимается как `0`. |
| `title` | Исходное значение — строка; после `trim` длина от 1 до 100 символов. |
| `priority` | Строго `low`, `medium` или `high`. |

В режиме редактирования источником id является `editingId`, а не `draft.id`, потому что поле id в форме заблокировано и не попадает в `FormData`. При этом `editingId` должен быть корректным и присутствовать в текущем массиве задач. Совпадение id с самой редактируемой задачей не считается дубликатом.

В `main.js` ошибки связываются с полями через `setCustomValidity`, `aria-invalid` и элементы `[data-error-for]`. При вводе в конкретное поле очищается ошибка только этого поля. После успешной операции форма сбрасывается, ошибки снимаются, список и сводка перерисовываются.

Дополнительно сервисные функции `addTask` и `updateTask` повторно проверяют данные. Это защитная граница: даже если проверка интерфейса будет обойдена, некорректная операция не должна изменить массив задач.

## 8. Восстановление и ошибки `localStorage`

| Ситуация | Ожидаемое поведение | Фактический результат |
|---|---|---|
| Ключ отсутствует | `loadTasks` возвращает копию исходного набора, `source: "initial"`. | Приложение показывает исходный набор. |
| Корректная запись | `loadTasks` возвращает копию задач, `source: "storage"`. | После перезагрузки данные восстанавливаются. |
| Повреждённый JSON | `JSON.parse` перехватывается, возвращается fallback и ошибка. | Показан исходный набор и предупреждение о некорректном JSON. |
| Несовместимая версия схемы | Запись отклоняется целиком, возвращается fallback. | Используется исходный набор, выводится сообщение о версии. |
| Неверная схема задач | `isValidTaskList` возвращает `false`, запись не используется частично. | Приложение не применяет повреждённый список. |
| Исключение при `setItem` | Операция остаётся в памяти вкладки, пользователь получает предупреждение. | После перезагрузки результат может быть потерян, но интерфейс не падает. |
| Сброс | Удаляется только текущий `storageKey`, исходный набор повторно не сохраняется. | Ключ удалён, показан исходный набор. |

В приложении не используется `localStorage.clear()`. Сброс вызывает `removeSavedTasks(window.localStorage, storageKey)`, поэтому не затрагивает другие учебные страницы того же origin.

## 11. Отладка

В `handleFormSubmit` установлена точка останова. При добавлении задачи `id = 20` зафиксированы значения:

**Сырой черновик из `FormData`:**

```js
{
  id: "20",
  title: "Изучить localStorage",
  priority: "high"
}
```

**Результат чистой проверки:**

```js
{
  ok: true,
  value: {
    id: 20,
    title: "Изучить localStorage",
    priority: "high"
  }
}
```

**Результат сервисной операции `addTask`:**

```js
{
  ok: true,
  tasks: [/* новый массив из 5 задач */]
}
```

**Записанная строка JSON:**

```json
{
  "version": 1,
  "tasks": [
    { "id": 1,  "title": "Изучить функции",          "completed": true,  "priority": "medium" },
    { "id": 4,  "title": "Подготовить модель задач",  "completed": false, "priority": "high" },
    { "id": 7,  "title": "Проверить методы массивов", "completed": false, "priority": "low" },
    { "id": 10, "title": "Оформить README",           "completed": true,  "priority": "medium" },
    { "id": 20, "title": "Изучить localStorage",      "completed": false, "priority": "high" }
  ]
}
```

**При ошибочном сценарии с повторным `id = 4` проверка вернула:**

```js
{
  ok: false,
  errors: {
    id: "Задача с таким id уже существует"
  }
}
```

После этого `addTask` не вызывалась, `saveTasks` не выполнялась, список остался прежним. Это подтверждает, что ошибка формы не приводит к частичному изменению состояния.

## 13. Вывод

В ходе практической работы была расширена реализация ПР3: добавлены форма создания и редактирования задачи, чистая прикладная валидация, сохранение состояния в `localStorage`, восстановление после перезагрузки и явный сброс к исходному набору. Логика модели, представления, валидации, хранения и координации интерфейса разделена по модулям.

Форма обрабатывается через событие `submit`, нативные ограничения HTML дополнены прикладными правилами. Ошибки связываются с полями и очищаются после исправления. В режиме редактирования id берётся из `editingId`, поскольку заблокированное поле не попадает в `FormData`. Функция `updateTask` не сбрасывает `completed` и не мутирует исходный массив.

Сохранённые данные проверяются по версии и полной схеме. Повреждённый JSON, неверная версия, неподходящая схема и исключения хранилища приводят к управляемому результату: приложение использует исходный набор и показывает предупреждение. Общий и индивидуальный наборы используют разные ключи, а сброс удаляет только текущий ключ, не затрагивая другие данные.

Регрессионные проверки сервиса, проверки новых модулей и браузерные сценарии пройдены. Общий контрольный сценарий и индивидуальный вариант № 7 подтверждают сохранение операций между перезагрузками и отсутствие смешивания наборов. Работа может быть сдана после добавления ссылки на отчёт в корневой `README.md` личного репозитория.
